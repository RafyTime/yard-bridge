Draft lifetime · updates · reset policy

One place decides how edits react to Game changes.

Problem
The editor’s interface is shallow around draft lifetime: its caller must know to remount it, and Seat approval triggers that reset too.
Solution
Move draft reconciliation into the editing module’s implementation; choose the preservation/reset policy before changing behavior.
Evidence
The parent keys on Game id and version; the editor snapshots rules with untrack; approving a Seat increments that version. This consequence follows from the code and was not separately reproduced in a browser.
Deletion test
Delete the parent’s reset knowledge only after concentrating that responsibility inside the editor; removing the key alone leaves a stale draft.
Seam / adapter
Keep the existing Svelte prop seam and Convex adapter; no new adapter framework or stored revision is justified.
Tests
Exercise editing during Seat approval, incoming rules changes, and switching Games through the editor’s interface. Keep server version checks and existing command-and-view tests.
  • locality: one draft lifetime
  • leverage: callers pass current state
  • depth: reset knowledge becomes internal
No ADR conflict. The server remains authoritative. Preserving a draft is a decision to discuss, not an assumed requirement.

Problem
The start module already has depth, but opening-effect tests cross its interface by counting Math.random calls and targeting Fisher–Yates positions.
Solution
Concentrate the complete deal and opening-state implementation behind an internal deterministic seam, while retaining atomic start behavior.
Deletion test
Moving only the rank switch creates a shallow module; the change earns leverage only if tests stop knowing shuffle positions and the module owns the complete initialization responsibility.
Seam / adapter
Prefer controlled initialization state over a generic random adapter; introduce an adapter only if two real implementations justify it.
Tests
Rules scenarios use the initialization interface; retain command-and-view tests for private hands, frozen rules, rejected starts, reconnection, and durable writes.
  • locality: opening invariants stay together
  • leverage: scenarios ignore shuffle mechanics
  • depth: one complete initialization responsibility
No ADR conflict. Internal organization only; avoid a general game engine until turn behavior needs one.

Keep the useful depth

requirePlayer already hides verified identity and durable-session checks. invitationContext concentrates shared invitation interpretation. The player fixture supports testing real commands and views. Repeated Seat lookups are modest; a generic persistence abstraction would add more interface than leverage today.
