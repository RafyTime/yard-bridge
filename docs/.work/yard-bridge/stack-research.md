# Stack research for Yard Bridge

Checked 27 September 2026. The first comparison below records two earlier hosted routes. The follow-up covers the user's preferred SvelteKit and Convex route. Prices and quotas are current documentation, not a cost forecast.

## Shared design, whichever service wins

- A React/TypeScript client built with Vite can deploy as static files. Installation requires a web app manifest; a service worker can cache the app shell, but active turns still need a connection to the authoritative game state. [Vite deployment](https://vite.dev/guide/static-deploy), [MDN PWA installation](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable). The connection requirement is a design inference.
- Send a proposed move to trusted server code. In one atomic operation, check identity, seat, turn, hand, card legality, current rules and state version; then write the next state and history event. Treat live messages as a prompt to refetch authorized state. This is a proposed design, based on [Postgres database functions](https://supabase.com/docs/guides/database/functions) or [Firestore transactions](https://firebase.google.com/docs/firestore/manage-data/transactions), not a vendor guarantee for the whole game.
- Keep each player's hand behind seat-specific authorization. A room invite identifies a game, not permission to inspect another hand. This is a design inference from [Supabase row-level security](https://supabase.com/docs/guides/database/postgres/row-level-security) and [Firestore security rules](https://firebase.google.com/docs/firestore/security/get-started).
- Store a complete game snapshot and an append-only record of accepted moves/round results in the database. Live event delivery and application logs are not indefinite history. This is a design recommendation; Supabase's database broadcast messages are [deleted after three days](https://supabase.com/docs/guides/realtime/broadcast), and its free API/database log retention is [one day](https://supabase.com/pricing).

## Option A: Vite/React + Supabase

Use Postgres tables for games, seats, private hands, rule snapshots and history. A database function can apply each move within the database, with row-level security for reads and tightly scoped write access. Supabase recommends private Broadcast channels for scalable database-change delivery; direct Postgres Changes are simpler to start with. [Database functions](https://supabase.com/docs/guides/database/functions), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [Realtime approaches](https://supabase.com/docs/guides/realtime/subscribing-to-database-changes). **Inference:** this route makes transactional scoring and long-lived relational history fairly direct, but moving complex card rules into SQL/functions may be less comfortable than TypeScript server code. An Edge Function can hold TypeScript rules and call a transactional database function for the final commit, adding another boundary to maintain. [Edge versus database functions](https://supabase.com/docs/guides/database/functions).

Supabase has native six-digit email OTP. Its default mail server only delivers to project-team addresses and is currently limited to two messages per hour, so real invitations require a custom SMTP provider even on the free plan. [Email OTP](https://supabase.com/docs/guides/auth/auth-email-passwordless), [SMTP limits](https://supabase.com/docs/guides/auth/auth-smtp). A specific EU project region such as Frankfurt, Ireland or Paris can be selected; the general Europe region may include non-EU locations. Selecting an EU database region alone does not establish where a separate SMTP provider processes mail. [Supabase regions](https://supabase.com/docs/guides/platform/regions), [SMTP setup](https://supabase.com/docs/guides/auth/auth-smtp). The latter residency point is an inference.

Supabase also documents direct Postgres connections from TypeScript Edge Functions, and recommends the transaction-mode pooler for serverless connections. **Inference:** card rules can live in a TypeScript Edge Function that validates and commits one move in a Postgres transaction, avoiding a separate application server and keeping complex rules out of SQL functions. The function must authenticate the caller and check seat authorization explicitly before any privileged write. [Edge Function database access](https://supabase.com/docs/guides/functions/connect-to-postgres), [connection modes](https://supabase.com/docs/guides/database/connecting-to-postgres).

The free plan currently includes 500 MB database storage, 200 peak Realtime connections and 2 million Realtime messages monthly, but it pauses projects after roughly one week of low activity. Supabase recommends regular off-site dumps for free projects. Pro starts at $25/month, does not auto-pause and includes daily backups retained for seven days. [Pricing](https://supabase.com/pricing), [pausing behavior](https://supabase.com/docs/guides/platform/free-project-pausing), [backups](https://supabase.com/docs/guides/platform/backups). **Inference:** the free tier is suitable for building and testing, but an indefinite, reliably available surprise game needs a backup routine and likely a paid project when launched.

## Option B: Vite/React + Firebase

Use Firebase Authentication, Cloud Firestore listeners for live state, and a callable Cloud Function to validate moves with a Firestore transaction. Transactions atomically update multiple documents and rerun on concurrent edits. [Callable functions](https://firebase.google.com/docs/functions/callable), [transactions](https://firebase.google.com/docs/firestore/manage-data/transactions), [listeners](https://firebase.google.com/docs/firestore/query-data/listen). **Inference:** TypeScript game logic fits naturally in the function, while private hands, shared scores and history need a careful document layout and security rules.

Firebase Authentication's built-in passwordless web sign-in is an **email link**, rather than a typed six-digit code. The free Spark plan currently allows only five email-link sign-in emails per day; Blaze raises that quota. An exact typed-code experience would need a custom mail and token flow, adding work. [Email-link sign-in](https://firebase.google.com/docs/auth/web/email-link-auth), [authentication limits](https://firebase.google.com/docs/auth/limits). Cloud Functions require the Blaze pay-as-you-go plan, even though that plan includes some no-cost usage. [Functions quotas and billing](https://firebase.google.com/docs/functions/quotas).

Firestore offers EU regions including Frankfurt and the Netherlands. Location affects database storage, while auth/mail and other services must be assessed separately for any residency promise. [Firestore locations](https://firebase.google.com/docs/firestore/locations). The free Firestore quota is 1 GiB stored, 50,000 reads and 20,000 writes per day; listeners incur reads when documents update. Backups and managed export/import require billing. [Firestore pricing](https://firebase.google.com/docs/firestore/pricing), [export/import](https://firebase.google.com/docs/firestore/manage-data/export-import). **Inference:** for a private table, raw volume is probably modest; the harder constraint is the chosen auth flow and the care needed to avoid exposing hidden hands through shared documents.

## Decision points for the technical grill

1. Is a typed email code a firm UX requirement? If yes, Supabase is the more direct hosted route; Firebase needs custom work. [Supabase OTP](https://supabase.com/docs/guides/auth/auth-email-passwordless), [Firebase email link](https://firebase.google.com/docs/auth/web/email-link-auth).
2. Is a $25/month baseline acceptable at launch for no auto-pause and managed daily backups, or should the first release use a free project with a documented restore/export routine? [Supabase plans](https://supabase.com/pricing), [Firebase backup pricing](https://firebase.google.com/docs/firestore/pricing).
3. Where should the card rules live? SQL/database functions give a compact transaction boundary; TypeScript server functions may be easier to change as the pair refines their variant. This is an implementation judgment, not a documented platform fact.

## Follow-up: SvelteKit, Convex and Railway

Checked against current first-party docs on 27 September 2026. The following is a third viable route, with its authentication and hosting choices kept separate.

### SvelteKit + TypeScript + Convex

Convex's Svelte client supports reactive queries and SvelteKit server rendering. A Convex mutation is a TypeScript function whose reads see one consistent state and whose writes commit together. Queries update subscribed clients over WebSockets. [SvelteKit integration](https://docs.convex.dev/client/svelte/sveltekit-server-rendering), [mutations](https://docs.convex.dev/functions/mutation-functions), [Convex architecture](https://docs.convex.dev/understanding/overview). **Inference:** one mutation can check seat, turn, selected cards and frozen rules, then commit the next game state and history entry. Split public table state from seat-specific queries so opponents never receive hidden hands; Convex advises authorization checks in backend functions. [Authorization guidance](https://docs.convex.dev/understanding/best-practices).

Convex Auth supports email OTPs and runs in the Convex deployment, but Convex calls it beta and its main documented clients are React and React Native. Its Svelte adapter is community maintained. The Convex Auth OTP guide configures an external email provider, using Resend as an example; it does not supply email delivery by itself. [Convex Auth](https://docs.convex.dev/auth/convex-auth), [Svelte auth adapters](https://docs.convex.dev/client/svelte/authentication), [OTP setup](https://github.com/get-convex/convex-auth/blob/main/docs/pages/config/otps.mdx). Better Auth also has an email OTP plugin, but requires the app to implement `sendVerificationOTP`; the Convex + Better Auth SvelteKit integration is community maintained and currently pins a Better Auth version in its setup guide. [Better Auth OTP](https://better-auth.com/docs/plugins/email-otp), [SvelteKit integration](https://labs.convex.dev/better-auth/framework-guides/sveltekit). **Inference:** Better Auth offers more auth options but adds a component, adapter and version compatibility to this small game's critical login path; Convex Auth is the narrower route if its beta status is acceptable.

The example `onboarding@resend.dev` in the Convex Auth guide is not evidence that email codes can reach arbitrary players in production without a sender domain. Resend's documented production workflow involves adding and verifying a domain for sending. [Convex Auth OTP example](https://github.com/get-convex/convex-auth/blob/main/docs/pages/config/otps.mdx), [Resend domain verification](https://resend.com/changelog/domain-verification-events). **Inference:** plan on owning a domain or finding another delivery provider with a documented shared production sender. Clerk offers managed email-code sign-in, but its production mail comes from the application's own domain with DNS setup, and Clerk's SvelteKit adapter is community maintained. It therefore does not remove the domain requirement here. [Clerk email-code option](https://clerk.com/docs/guides/configure/auth-strategies/sign-up-sign-in-options), [Clerk email delivery](https://clerk.com/docs/guides/development/troubleshooting/email-deliverability), [Clerk SvelteKit support](https://clerk.com/docs).

Convex's Free plan lists 1 million function calls per month, 0.5 GB database storage and 1 GB data egress. Free has hard caps; extended overuse may make functions return HTTP errors. Its pricing page lists a selectable data region. Free/Starter allow manual backups, at most two stored per deployment, each kept seven days; automated daily or weekly backups require Professional. A CLI export can produce an off-site ZIP. [Limits](https://docs.convex.dev/production/state/limits), [pricing FAQ](https://www.convex.dev/pricing/faq), [pricing](https://www.convex.dev/pricing), [backups](https://docs.convex.dev/database/backup-restore), [export CLI](https://docs.convex.dev/cli/reference/export). I found **no official statement of Supabase-style automatic pausing for an inactive Convex Free deployment**; the limits page's 30-day "idle deployment" definition concerns deployment-fee waivers on Business/Enterprise, not Free project suspension. [Deployment classes](https://docs.convex.dev/production/state/limits). Do not infer an indefinite service guarantee from that silence.

Convex says its Ireland data region is available on Free. A deployment's region cannot yet migrate automatically, so choose the region at creation if EU location matters. [Convex EU region announcement](https://news.convex.dev/we-finally-got-our-eu-visa/).

### Railway as frontend host

Railway's current Free plan is $0 with $1/month in included resource usage. Hobby costs $5/month and includes $5 of usage, so the minimum Hobby bill remains $5. [Railway plans](https://docs.railway.com/pricing/plans). Its optional Serverless setting sleeps a container after at least five minutes without outbound packets; traffic wakes it, with a cold start and a possible first-request 502. Database connections or telemetry can prevent sleep. [Railway Serverless](https://docs.railway.com/deployments/serverless). **Inference:** if SvelteKit only serves a static client and Convex handles live state, static hosting avoids paying for or waking a Node process. If SvelteKit SSR is chosen, Railway hosts that process; its sleep setting trades lower idle usage for occasional slower or failed first requests. Do not run the authoritative game state in a sleeping frontend container. [SvelteKit adapters](https://svelte.dev/packages), [Convex SvelteKit SSR](https://docs.convex.dev/client/svelte/sveltekit-server-rendering).

Railway's frontend guide describes SvelteKit `adapter-static` served by Caddy as its cheapest rendering option, but Caddy remains a service with resource usage. A static build removes the need for a SvelteKit application server; it does not establish a zero bill under every workload. [Railway rendering guide](https://docs.railway.com/guides/ssr-ssg-isr).

### No-domain email delivery

Convex Auth's OTP provider lets the app implement `sendVerificationRequest`, so an HTTP email API can be used instead of the guide's Resend example. It also rate-limits failed code attempts. [Convex Auth OTP guide](https://github.com/get-convex/convex-auth/blob/main/docs/pages/config/otps.mdx). This solves code generation and verification, but not sender identity.

Google documents SMTP and app passwords for a personal Gmail account, though it explicitly recommends Google sign-in over app passwords. Using a personal account for automated login mail would couple the game's availability to that account and credential. [Gmail SMTP settings](https://support.google.com/mail/answer/7104828?hl=en), [Google app-password guidance](https://support.google.com/mail/answer/185833?hl=en-IN). Brevo's Free plan includes transactional mail, but its current sender guidance says a free email address will be replaced with a Brevo address and describes this as a temporary delivery measure. [Brevo Free plan](https://help.brevo.com/hc/en-us/articles/208580669-FAQs-What-are-the-limits-of-the-Free-plan), [Brevo sender guidance](https://help.brevo.com/hc/en-us/articles/14925263522578-Comply-with-Gmail-Yahoo-and-Microsoft-s-requirements-for-email-senders). **Inference:** a personally owned mail domain is the cleanest production route for reliable typed codes, even if the app keeps its Railway-provided URL. If no domain is firm, a managed social sign-in is a simpler launch compromise than maintaining a mail workaround.

### UI and code structure

shadcn-svelte distributes editable Svelte component code and includes controls such as buttons, dialogs, collapsibles and OTP input. [Project overview](https://www.shadcn-svelte.com/docs), [component list](https://shadcn-svelte.com/docs/components). **Inference:** use selected controls for rule settings, invites and authentication, then draw the card table and interactions as custom UI to keep the Offsuit-inspired look. Effect models success, error and required dependencies in its TypeScript `Effect` type. [Effect type](https://effect.website/docs/v4/getting-started/the-effect-type). **Inference:** that adds a second application programming model to a small, already transactional game; plain TypeScript domain functions with explicit result types are enough at launch unless the team already knows Effect well.
